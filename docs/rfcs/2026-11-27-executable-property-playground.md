# RFC: Executable property-testing playground

## Problem and scope

The owner wants to review small executable properties and useful counterexamples
instead of manually reviewing every behavior of agent-written code. A scenario
should prepare an environment, run a real executable through a sequence of
operations, check a stated law, and reduce a failing case into a replayable example.

On 2026-11-27 the owner authorized a reversible project-harness experiment in
Tauten, tracked in [#103](https://github.com/tauten-dev/tauten/issues/103). This
document proposes its design for review. The experiment is not authorization to
publish a production API or impose gates on other projects. A local prototype
exists; the PR publishing these RFCs contains documentation only.

## Proof obligations and limits

No checker, kernel, admission, badge or proof-record decision changes. This
standalone testing playground is tested and unproved, including its generators,
assertions, shrink traversal, serialization and OS/container interactions. Passing
a finite campaign establishes neither a theorem nor exhaustive coverage.

Aeneas/Lean can establish laws of the extracted model under its assumptions. This
harness exercises the executable, its command interface, files and integration
behavior. These are complementary sources of evidence; test results do not become
proof claims. Future integration into Tauten's admission decisions requires a
separate accepted design and the normal kernel/proof obligations.

## Reuse and ownership

| Layer | Proposal | Responsibility |
|---|---|---|
| Generation and shrink trees | Existing Rust Proptest library | Generate values/sequences and offer simpler candidates |
| Isolated execution | Existing Docker engine and prepared images | Execute each candidate in a fresh container |
| Tauten playground | Small unpublished Rust runner | Lifecycle, real processes, observations, failure identity, concrete replay |
| Project adapter | Ordinary project-owned code | Valid generators, setup hooks, actions, independent oracle and named properties |

Proptest supplies the algorithms for shrinking values and sequences. Our bounded
traversal retains candidates that still fail the original named property; it is
not a replacement property-testing engine. Rust is the initial adapter language,
not a restriction on the language of the executable under test.

No new scenario DSL, expression evaluator or universal property inference system
is proposed. TOML could later hold campaign settings if repeated usage warrants
it; domain properties and setup remain ordinary code initially.

## Scenario contract

An adapter provides:

1. A serializable case generated by a Proptest strategy. Include initial fixtures,
   operation sequences and any random choices that affect replay.
2. A setup hook that materializes that case in the fresh environment.
3. An executor that invokes the actual binary with bounded argv/stdin operations
   and observes structured output or resulting files.
4. A smaller, independent oracle that returns pass, a named property failure with
   expected/actual observations, or a rejected invalid case.
5. Target and adapter identities, plus explicit environment configuration.

State persists between operations of one scenario. The entire scenario starts
fresh for every generated case, shrink attempt and replay. Invalid candidates are
rejected, never counted as passes. Prefer generators and shrinkers that preserve
validity by construction: removing an operation must not leave a later operation
referring to a resource that was never created.

Infrastructure errors abort distinctly from property failures. A timeout, missing
tool, failed setup, exhausted generation budget or failed cleanup must not be
reported as a passing campaign or shrunk into an unrelated product defect.

A conceptual Strop scenario is: generate initial text and a valid edit transaction;
run the edit through headless mode; assert the expected edited buffer; undo; assert
the initial buffer; redo where supported; assert the edited buffer again. Checking
the intermediate edit prevents an executable that ignores every command from
passing the round-trip law. The adapter uses the existing settle/event boundary,
not timing sleeps. Exact commands belong to the adopter's documented interface.

## Campaign, shrinking and replay

For each generated case, prepare, execute, observe and check. On the first product
failure, traverse the supplied shrink tree within a budget. Retain only candidates
that fail the same property ID. Re-execute the final candidate in another fresh
environment before recording it. Report a smaller reproducer, not a globally
minimal one; expose budget exhaustion and non-reproduction honestly.

Save the concrete case and generated fixtures, target/adapter identity, resolved
environment, expected/actual observations and command trace. A seed helps explain
how a case was found but is not sufficient for long-lived replay across library
versions. Replay checks identity; checking a repaired target requires an explicit
changed-target override. The detailed contract is in
[the environment/replay RFC](2026-11-27-scenario-environments-and-replay.md).

## Alternatives

- [Proptest](https://proptest-rs.github.io/proptest/intro.html) fits Tauten's Rust
  environment and supplies generation and shrinking. It does not itself provide
  our complete executable sandbox and portable replay contract.
- [Hypothesis stateful testing](https://hypothesis.readthedocs.io/en/latest/stateful.html)
  already supports action sequences and shrinking and can invoke executables from
  Python. For Gripsack's existing pytest suite, a thin Hypothesis adapter may be
  cheaper than introducing a Rust test runner; compare both before choosing.
- [fast-check model-based testing](https://fast-check.dev/docs/advanced/model-based-testing/)
  is a similar option for a project whose natural test host is JavaScript/TypeScript.
- [TSTL](https://github.com/agroce/tstl) is an existing scenario-language precedent.
  Adopting a new DSL is unnecessary until ordinary adapters show a concrete gap.

The selection criterion is useful defects and maintainable tests, not adoption of
one shared runtime everywhere. Keep shared machinery only where multiple trials
show it removes repeated work.

## Delivery and acceptance

Keep the experiment in an unpublished standalone package at playground/scenarios,
with its own workspace/lockfile. Do not alter published crates or proof fingerprints.

The first control is a queue executable with a planted FIFO defect and an independent
list model. The correct executable must pass; the faulty mode must yield a reduced
case that reproduces. A no-op control must fail a check of actual changed state.
Then qualify environment/reset/replay behavior before making any adopter gate required.

| Order | Issue | Observable behavior |
|---|---|---|
| Foundation | [#103](https://github.com/tauten-dev/tauten/issues/103) | Executable experiment, generation, shrinking, concrete replay |
| Qualification | [#104](https://github.com/tauten-dev/tauten/issues/104) | Fresh environments, error classification, bounded execution, replay |
| First trial | [#105](https://github.com/tauten-dev/tauten/issues/105) | Strop edit/undo/redo through its headless interface |
| Second trial | [#106](https://github.com/tauten-dev/tauten/issues/106) | Gripsack owned-content updates preserve unmanaged bytes |
| Third trial | [#107](https://github.com/tauten-dev/tauten/issues/107) | Writfold source changes invalidate scoped gate results |

Each trial records a named planted defect or historical regression, a useful reduced
reproducer, replay behavior, runtime, adapter size and fixture maintenance. Keep or
reject the shared integration on that evidence. Do not freeze a public API from
one toy example. Project-specific implementation changes are separately reviewed
in their own repos; the linked Tauten issues track the experiment.

## Boundaries

Sequential generated testing does not implement #13's storage simulator or #17's
bounded world explorer. Deterministic scheduling, fault injection and exhaustive
state exploration are separate capabilities. Docker does not by itself control
clock values, randomness or concurrent scheduling. Property quality remains a
review task: a generated input is useful only when the oracle tests the intended
behavior without repeating the implementation's mistake.

## Validation record

The local prototype was built with Rust 1.98.0. Eleven native integration tests,
formatting checks and Clippy with warnings denied passed. Tests included actual
queue execution, a no-op negative control, same-property shrinking, concrete
replay, changed-target refusal, clean state, cleanup failures, deadlines, output
bounds and process-group cleanup. Seed 7 reduced the planted FIFO defect from 16
operations to push(0), push(-1), pop(); the correct mode passed 100 generated cases.

The two live Docker tests and Tauten's full container gate have not been run in
the development environment, which has no Docker daemon. Proposed CI wiring is
not evidence of a CI pass. No adopter integration has been implemented. This
RFC publication does not publish the local prototype code or its workflow.
