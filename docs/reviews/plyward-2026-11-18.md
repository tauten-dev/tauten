# Plyward handover vs tauten: critique and plan changes

2026-11-18. Read-only review; nothing was built or run. Paths: `T/` = `/home/tarek/workspace/tauten`, `P/` = the extracted `plyward-handover/` in the session scratchpad, `W/` = `/home/tarek/workspace/writfold`.

## Verdict

**Do not pivot.** Plyward is a proof-process specification with no tool: `P/evidence/STATUS.md` says "No Plyward checker, contract macro, CLI, formal semantics or implementation proof has been built", and all 31 obligations are pending. tauten has an exercised checker, macros, a ratchet and a validated benchmark harness. Plyward's own first milestone (F00, toolchain bootstrap) is already done in `W/proofs` (Lean v4.35.0, Aeneas `nightly-2026.11.07`, Charon nightly-2026-09-17, drift check, axiom audit, 214 mutants).

What Plyward adds is (a) a sharp list of ways a refinement or capability can be bypassed, (b) two honest negative controls, and (c) a few proof-hygiene rules. Reading tauten against that list turned up three real defects in tauten (section 1). Those are worth more than any of Plyward's new mechanisms.

## 1. What tauten should take

### 1a. Defects in tauten that Plyward's checklists expose (fix these)

1. **`#[refined]` can be bypassed by a derive.** `T/crates/tauten-macros/src/lib.rs` (`expand_wrapper`) copies every user attribute onto the generated struct (`#(#attrs)*`). So `#[derive(Default)]` or `#[derive(serde::Deserialize)]` on a refined type produces values that never went through `try_new`. `T/docs/MAPPING.md` rates refinements strength **C**; that is not true today. Plyward lists exactly this in `P/spec/REFINEMENTS.md` ("No unchecked `From<Raw>`, unchecked default ... Deserialization ... validate before creating the trusted value"), and its nutype example tests JSON 101 and 255 being rejected. No tauten test covers it (`T/crates/tauten/tests/ui/` has six cases, none for derives).
   Fix: allowlist derives on `#[refined]` (Debug, Clone, Copy, PartialEq, Eq, PartialOrd, Ord, Hash, Serialize); reject Default, Deserialize and unknown derives with a clear error; optionally offer a `serde` flag that emits `#[serde(try_from = "Inner")]`.
2. **The A001 repair hint names a type that does not exist.** `T/crates/tauten-check/rules.toml:259` (also README and `docs/RULES.md:269`) says "for example `&tauten::cap::FsRead`". There is no `FsRead` in `T/crates/tauten/src/cap.rs`. An arm-C agent following the hint gets a compile error. This is a benchmark confound; fix before the pilot runs, or record it if the pilot has started.
3. **Authority can be minted in core without tripping A002.** A002 is a syntactic scan for `Authority::acquire` (`T/crates/tauten-check/src/scan.rs:106-125`). I found no ban on `cap_std::ambient_authority` or `Dir::open_ambient_dir` in `rules.toml`, so a core crate with the `fs` feature can open any directory itself. An alias (`use ...::Authority as A`) or a function-pointer use (`let f = Authority::acquire;`) probably also slips the scan; I did not test that. Fix: add the cap-std ambient entry points to the A001 banned list, and enforce `acquire` through clippy's resolved `disallowed-methods` as well as the scan.

### 1c. Decide by measurement, not argument

Plyward's "instance origin" and "freshness" are plausible agent defect classes (span from document A used on B; a check done before a mutation). Nobody knows how often agents make them. Add them as defect classes to two or three **held-out benchmark tasks**. **Revised 2026-11-19:** prioritise by measurement; do not eliminate by it. If, with at least 30 arm-A trials on at least three tasks able to exhibit them, these classes are under 5% of arm-A escaped defects, brands and freshness are deferred to the next planning review (or sooner on new benchmark data, another model or a field defect). If they cluster there, raise the priority and start with a runtime owner/generation check. A class no task can exhibit is "not measured", never "dropped".

## 3. Plyward claims that are wrong, over-ambitious or not checkable

- **Wrong fact.** `HANDOVER.md` section 1 says "approximately 22,000 Lean lines"; the real figure is about 222k. It also states the Sovel repo and writfold were not audited, so it plans F00 without knowing writfold has the pins.
- **Brand example is weaker than presented.**
  - `brands.rs` `Snapshot::slice` still does `&self.text[...]`, a runtime bounds and char-boundary check that can panic. `CHECKS.json` records C-SNAPSHOT as release plan "static-only"; that is inaccurate without `get_unchecked`, which Plyward bans. It would also fail TAU-P003.
  - Its doctest is a bare `compile_fail` with no error code (the other four pin E0597/E0308/E0080), so any compile error passes it. tauten's trybuild `.stderr` files are stronger evidence.
  - A `make_guard!` brand is a stack local. A branded `Snapshot` cannot be returned from the scope that made it, stored in a long-lived struct, or serialized. Plyward concedes persisted handles need runtime checks anyway.
  - Aeneas erases lifetimes, so the brand contributes nothing in the Lean model; the index must be proved safe from an explicit invariant regardless.
- **GhostCell example solves a problem the profile forbids.** `increment(&GhostCell, &mut GhostToken)` is strictly worse than `increment(&mut CounterValue)`. GhostCell pays only for shared graphs (`Rc<GhostCell>`), which TAU-K001 bans in the kernel. It is built on `UnsafeCell`; I expect it not to extract, but did not test.
- **Proposed contract notation is not checkable.** In `proposed-contracts.rs.txt`: `allocate` as an effect cannot be decided soundly without whole-program analysis (any generic call or `Drop` may allocate); `on_ok_origin(slice_of(source, range))` is a functional-correctness theorem, not a checker fact; `result_captures` is unknowable across `dyn Fn` and opaque cross-crate types.
- **F02 (static discharge, certificate-checked check elimination)** optimises away a `<= 100` comparison. No mission value.
- **Three proof systems** (Lean, optional Verus, TLA+/TLAPS for F07) with "explicit bridge obligations" is a composition problem nobody has budget for.
- The capability, origins, effects and refinement examples are otherwise correct and honestly caveated. The examples pin Rust 1.100.0; tauten and writfold pin 1.98.0.

## 5. Should M3 change shape?

Keep the plan (generalise `W/proofs`: extract, drift, `lake build`, axiom audit, mutants). Do not adopt Plyward's F00 to F07 ladder. Change these points:

1. **Probe first (0.5 day).** Check whether Charon/Aeneas extract tauten's own macro output. `#[refined]` expands to `contract::holds(&value, |v| ...)` (a generic `FnOnce` closure) and contracts wrap the body in an immediately-invoked closure (`lib.rs`, `expand_contracts`). Closure support in Aeneas is limited; I did not test this. If extraction fails, either emit a closure-free expansion for kernel crates or state that kernel functions use hand-written checks and theorems replace `#[ensures]`. Decide before templating. This is Plyward's one good procedural point ("compare macro-generated code with a tiny explicit constructor first").
2. **Starter kernel = the benchmark host's kernel crate** (`T/bench/hosts/ledger`), not a toy. Theorems: a refined scalar's `try_new_ok_iff` (sound, complete, raw value preserved: the three of Plyward's eight F01 targets that are expressible over extraction) and the fee calculation's total spec (overflow returns `Err`). This allows a later "arm D" measuring the proof tier.
3. **Proof subsumes lints.** Resolve the dry-run finding (`T/docs/dry-runs/writfold-2026-11-18.md`: 231 N001/P003 findings in a proved kernel): a `proofs/claims.toml` maps Rust function path to theorem and mutants; `cargo tauten check` downgrades N001/P003 for functions with a claim, and the gate fails if a listed claim is missing from the audit.
4. **Coverage report, not a contract generator.** Report extracted `pub fn` count versus those with at least one theorem. Do not generate Lean statements from `#[ensures]`; that is the generator-correctness trap.
5. **Template rules:** every `_spec` theorem has an `_iff` or a witness; one-page `TRUST.md`; JSON outcomes `proved | drift | build-failed | audit-failed | mutant-survived | tool-missing`.
6. Time box (3 agent-days) and ordering (after the pilot, owner decision 5) stay as they are.
